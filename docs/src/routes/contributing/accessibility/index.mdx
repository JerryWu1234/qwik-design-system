# Accessibility

<Image src={accessibility} alt="Accessibility" />

Building accessible applications isn't just about compliance—it's about crafting experiences that **everyone** can use, regardless of their abilities. When you make accessibility a priority, you're not just checking a box; you're opening your application to millions of people who rely on assistive technologies, creating a better user experience for everyone, and building products that truly matter.

**The Americans with Disabilities Act (ADA)** requires applications to be accessible to people with disabilities, but beyond legal requirements, accessibility:

- **Expands your reach** - Over 1 billion people worldwide have disabilities
- **Improves usability** - Features like keyboard navigation and clear focus states benefit all users
- **Enhances SEO** - Semantic HTML and proper structure help search engines understand your content
- **Builds better products** - Accessible design often leads to cleaner, more maintainable code

## For Contributors

**Contributing to QDS?** Here's your quick checklist:

### Required ✅

Before submitting a PR, ensure:

1. **Automated tests pass** - Run `pnpm test` (includes axe accessibility checks)
2. **Basic keyboard testing:**
   - Press `Tab` to navigate through interactive elements
   - Press `Enter`/`Space` to activate buttons and controls
   - Press `Esc` to close overlays/menus
   - Verify focus indicators are visible
   - Check that focus returns correctly

As long as the keyboard testing matches the controls in the component, and is a widely used pattern, that is enough.

### Optional but Appreciated 🌟

- Run integrated accessibility testing on your changes (see [Level 2: Automated Testing](#level-2-automated-testing))
- Test with a screen reader if you're familiar with one (see [Screen Reader Testing](#2-screen-reader-testing))
- Review keyboard shortcuts in [Manual Keyboard Navigation Testing](#1-manual-keyboard-navigation-testing)

> **Everything else in this document is educational.** Read what interests you, dive deep into the testing pyramid, explore the resources—but don't feel overwhelmed. The checklist above is what we expect from contributors.

> **Warning:** DO NOT blindly follow the [ARIA APG](https://www.w3.org/WAI/ARIA/apg/) patterns. While it's a useful reference, many patterns are incomplete or outdated and do not guarantee production-ready accessibility. Always test with real assistive technologies.

## The Accessibility Testing Pyramid

Think of accessibility testing like a pyramid—automated tests form the broad base, catching obvious issues quickly and cheaply. As you move up, tests become more nuanced and valuable, but also more time-intensive.

**The Pyramid (from bottom to top):**

1. **Linters & Type Checks** - Catch issues during development
2. **Automated Tests** - Fast, catches ~30-40% of issues  
3. **Manual Testing** - Keyboard navigation and screen readers
4. **User Testing** - Most valuable, most expensive

### Level 1: Linters & Static Analysis

**Catch issues before they reach production.** These tools run as you code, providing instant feedback.

#### Recommended Tools:
- **[eslint-plugin-jsx-a11y](https://github.com/jsx-eslint/eslint-plugin-jsx-a11y)** - Static AST checker for JSX accessibility rules
- **[axe-linter](https://www.deque.com/axe/devtools/)** - Deque's axe DevTools Linter extension for VS Code
- **TypeScript** - Catch prop and attribute errors at compile time

### Level 2: Automated Testing

**Catch 30-40% of accessibility issues automatically.** While automated testing can't catch everything, it's an essential foundation that runs fast and consistently.

#### In Your Test Suite: Vitest + Axe

In QDS, we use Vitest with axe-core to validate accessibility in our component tests:

```tsx
test("Radio Group should meet axe accessibility requirements", async () => {
  const screen = render(<Basic />);

  await expect.element(Root).toBeVisible();

  const results = await axe.run(screen.container);

  expect(results.violations).toHaveLength(0);
});
```

This approach ensures every component meets baseline accessibility requirements before merging.

#### Browser Extensions

Test in your browser as you develop:

- **[Lighthouse](https://developers.google.com/web/tools/lighthouse)** - Built into Chrome DevTools, provides accessibility audits
- **[axe DevTools](https://www.deque.com/axe/devtools/)** - The most accurate automated accessibility testing tool
- **[WAVE](https://wave.webaim.org/extension/)** - Visual feedback about accessibility issues
- **[WCAG Color Contrast Checker](https://chromewebstore.google.com/detail/wcag-color-contrast-check/plnahcmalebffmaghcpcmpaciebdhgdf)** - Quickly check color contrast ratios

> Color contrast checker is mainly for the examples we use in the docs site, as the headless components are unstyled.

#### Continuous Integration & Monitoring

**Catch issues before deployment:**

- **[Sauce Labs](https://saucelabs.com/)** - Cross-browser automated accessibility testing
- **[Ghost Inspector](https://ghostinspector.com/)** - Automated browser testing with accessibility checks
- **[Google PageSpeed Insights](https://pagespeed.web.dev/)** - Includes accessibility scoring
- **[Pa11y](https://pa11y.org/)** - Command-line tool for CI/CD pipelines

### Level 3: Manual Testing

**Manual testing should never be skipped.** Automated tools catch only 30-40% of accessibility issues. The rest require human judgment and real assistive technology testing.

> **For contributors:** Basic keyboard testing (covered in the checklist above) is required. Screen reader and speech recognition testing are typically performed by maintainers during component development—but we'd love it if you want to learn!

#### 1. Manual Keyboard Navigation Testing

All interactive elements must work without a mouse. Use just your keyboard to check:

- All buttons, links, fields, and widgets can be reached with `Tab`/`Shift+Tab`.
- You always see a clear focus indicator when tabbing.
- The tab order matches what's logical/visible on the page.
- `Space` and `Enter` activate buttons and toggles.  
- `Space` activates checkboxes and radios (when focused).  
- `Enter` activates links and buttons, but does **NOT** activate most inputs (like text fields) unless they submit a form or have special handlers.
- Arrow keys and `Home`/`End` work in widgets like tabs, navbars, menus, radio groups.
- `Esc` closes overlays/menus, and focus returns to the trigger.

**Main keys to test:**  
`Tab` / `Shift+Tab` (move focus)  
`Enter`/`Space` (activate)  
Arrow keys (navigate in groups)  - Up/Down/Left/Right
`Home`/`End` (jump in groups)  
`Esc` (close overlays)

> Look at the existing browser tests to practice, you can find the code in the `components/src/` folder. The file name is `*.browser.tsx`.


#### 2. Screen Reader Testing

**Test with actual screen readers**—this is where you catch the issues that matter most:

**Platform Pairings:**
- **Windows:** NVDA (free) or JAWS (paid) with Firefox/Chrome
- **Mac:** VoiceOver (built-in) with Safari
- **iOS:** VoiceOver (built-in) with Safari
- **Android:** TalkBack (built-in) with Chrome

**What to check:**
- ✅ Does the screen reader **announce meaningful content** for all elements?
- ✅ Do **form fields** have clear, associated labels?
- ✅ Are **error messages** announced and associated with their fields?
- ✅ Do **status updates** announce without stealing focus (live regions)?
- ✅ Are **headings** properly nested and navigable?
- ✅ Can you **navigate landmarks** to jump between page sections?
- ✅ Do **custom components** (tabs, accordions, etc.) announce their state?

#### 3. Speech Recognition Testing

**Often overlooked but critical** for users with motor disabilities who cannot use a keyboard or mouse:

**Tools:**
- **Windows:** Dragon NaturallySpeaking (paid), Windows Speech Recognition (built-in)
- **Mac:** Voice Control (built-in)

**What to check:**
- ✅ Can users **activate buttons and links** by voice commands?
- ✅ Do elements have **visible labels** that match their accessible names?
- ✅ Are interactive elements **large enough** to be reliable click targets?

### Level 4: User Testing

**The gold standard.** Nothing beats real users with disabilities testing our components.

> **For contributors:** This level is primarily for maintainers and long-term project improvement. Don't worry about coordinating user testing for your PR!

We gather user feedback through:

- Feedback from people building with our components—we encourage them to report accessibility issues and suggest improvements
- Accessibility-related issues and discussions on GitHub and in community forums
- Direct feedback from users with disabilities and accessibility advocates
- Real-world usage uncovering problems we can't predict through testing alone

## Qwik-Specific Accessibility Patterns

Most accessibility features in Qwik work through standard HTML attributes added on initial render. However, Qwik has unique features for managing attributes, elements, focus, and state.

### Attributes and State

In this example, we're creating an accessible toggle button that properly announces its state to screen readers:

```tsx
import { component$, useSignal, $ } from '@builder.io/qwik';

export const ToggleButton = component$(() => {
  const isPressed = useSignal(false);

  const handleClick$ = $(() => {
    isPressed.value = !isPressed.value;
  });

  return (
    <button 
      onClick$={handleClick$}
      aria-pressed={isPressed.value}
    >
      Toggle
    </button>
  );
});
```

**Key principle:** Use reactive state (signals, stores, props) to manage attributes dynamically.

#### Data Attributes

For `data-*` attributes, we can use the signal value directly.

```tsx
const isPressed = useSignal(false);

return (
  <button 
    aria-pressed={`${isPressed.value}`}  // String "true" or "false"
    data-pressed={isPressed.value}  // Present or absent
  >
    Toggle
  </button>
);
```

### Refs for Focus Management

Signals in Qwik double as refs, allowing you to manage focus programmatically:

```tsx
import { component$, useSignal, $ } from '@builder.io/qwik';

export const FocusExample = component$(() => {
  const inputRef = useSignal<HTMLInputElement>();

  const focusInput$ = $(() => {
    inputRef.value?.focus();
  });

  return (
    <>
      <input ref={inputRef} type="text" />
      <button onClick$={focusInput$}>Focus the input</button>
    </>
  );
});
```

#### Merging Refs

When building components that accept refs from consumers:

```tsx
export const Button = component$<ButtonProps>((props) => {
  const internalRef = useSignal<HTMLButtonElement>();

  return (
    <button 
      ref={(el) => {
        // Set internal ref
        internalRef.value = el;
        
        // Forward to consumer ref if provided
        if (props.ref) {
          props.ref.value = el;
        }
      }}
    >
      <Slot />
    </button>
  );
});
```

This is automatically handled by the `Render` component.

## JSX in Qwik

There are key differences between JSX and HTML that impact accessibility:

### Self-Closing Tags

JSX requires explicit closing for all elements:

```tsx
// ❌ Invalid JSX
<img src="/logo.png" alt="Company logo">
<input type="text" id="name">

// ✅ Valid JSX
<img src="/logo.png" alt="Company logo" />
<input type="text" id="name" />
```

### Case Sensitivity

**Tags:** Must be lowercase:

```tsx
// ❌ Invalid
<MAIN><H1>Title</H1></MAIN>

// ✅ Valid
<main><h1>Title</h1></main>
```

**Attributes:** Use camelCase (except `data-*` and `aria-*`):

```tsx
// ❌ Invalid
<video autoplay={true} />
<label for="email">Email</label>

// ✅ Valid
<video autoPlay={true} />
<label for="email">Email</label>

// ✅ Exceptions: data-* and aria-* stay kebab-case
<button 
  data-test-id="submit" 
  aria-label="Submit form"
/>
```

### Event Handlers

Qwik uses the `$` suffix for lazy-loaded event handlers:

```tsx
export const Counter = component$(() => {
  const count = useSignal(0);

  return (
    <button onClick$={() => count.value++}>
      Count: {count.value}
    </button>
  );
});
```

## Cross-Platform Testing Strategy

Testing across platforms ensures your application works for everyone.

> **For contributors:** Cross-platform testing is typically handled by maintainers. This section is educational if you want to understand our testing approach or set up your own accessibility testing workflow.

### Establish a Baseline

1. **Choose a primary platform** for development testing (e.g., NVDA + Firefox on Windows)
2. **Test regularly** on this platform during development
3. **Document your setup:** Browser version, screen reader version, OS

### Expand Testing

**Desktop:**
- Windows: NVDA (free), JAWS (paid), Narrator (built-in)
- Mac: VoiceOver (built-in)

**Mobile:**
- iOS: VoiceOver (built-in)
- Android: TalkBack (built-in)

**Browsers:**
- Chrome/Edge, Firefox, Safari

### Recommendation: Keep Testing Notes

If you are doing cross-platform testing:

We recommend keeping a simple log of your manual accessibility testing sessions. Jot down:
- Which platforms and tools you tested with
- Any problems or bugs you encountered
- The steps you took to resolve them

> **Suggestion:** Whenever you fix an issue, retest on all relevant platforms to ensure you didn’t introduce regressions elsewhere.
